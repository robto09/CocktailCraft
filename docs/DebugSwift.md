# DebugSwift Guide for CocktailCraft

## Overview

This guide documents the DebugSwift integration in the CocktailCraft iOS app: installation, how it is kept out of Release builds, day-to-day usage, and QA testing scenarios. DebugSwift is a comprehensive debugging toolkit for QA and development purposes. The integration is **DEBUG-only** and is not included in release builds (see [Keeping DebugSwift Out of Release](#keeping-debugswift-out-of-release)).

## Requirements

- **iOS deployment target**: 17.0 (DebugSwift needs 14.0+)
- **Xcode**: 26.0+ (the app needs the iOS 26 SDK)
- **Swift**: the app targets use Swift 5.10 (`SWIFT_VERSION` in `iosApp/project.yml`); Swift Package Manager builds DebugSwift in the language mode its own `Package.swift` declares, so the two do not need to match

## Installation

> The Xcode project is generated by XcodeGen: `iosApp/project.yml` is the
> source of truth for all build settings. Never edit `project.pbxproj` by hand —
> change `project.yml`, then run `xcodegen generate`.

### Step 1: Swift Package Manager Integration
DebugSwift is a Swift package declared under `packages:` in `iosApp/project.yml`
and added as a dependency of the app target:

```yaml
packages:
  DebugSwift:
    url: https://github.com/DebugSwift/DebugSwift
    # Tag 1.7.13.1 — a four-part tag is not valid SemVer, so SPM pins it by commit
    revision: 3dc1781a855f3fa91c5f7fe3868717fe62ff3c4e
```

The resolved version is locked in the committed
`CocktailCraft.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`.
To upgrade, pick a three-part release tag (e.g. `1.7.19`), switch to
`exactVersion:`, regenerate, and commit the updated `Package.resolved`.

### Keeping DebugSwift Out of Release
SPM cannot link a package for only some build configurations, so
`project.yml` enforces Debug-only in three layers:

1. **Code** — every `import DebugSwift` and every use sits inside `#if DEBUG`,
   so Release code never references it.
2. **Link** — the Release configuration sets
   `EXCLUDED_SOURCE_FILE_NAMES: DebugSwift.o`, which drops the package's
   object file from the app's link. (Xcode still *compiles* the package in
   Release; it just is not linked.)
3. **Bundle + guard** — the **Strip DebugSwift from Release** build phase
   deletes the `DebugSwift_DebugSwift.bundle` resources Xcode still copies in,
   then fails the build if DebugSwift turns up in any of four places (for
   example, if a future Xcode renames the package object and the exclusion
   stops matching):
   - `nm`: DebugSwift symbols in the binary's symbol table;
   - `grep -a`: DebugSwift in the binary's bytes — Swift type metadata and
     Objective-C class names stay in the binary even when the symbol table is
     stripped, so this still works on a stripped build;
   - `otool -L`: a linked DebugSwift dylib/framework (if the package ever
     ships as a dynamic product);
   - `find`: any other `*DebugSwift*` file left in the app bundle.

   Limitations: the exclusion itself still depends on the object file being
   named `DebugSwift.o`; the guard is what catches a rename. The string check
   would also trip if Release code ever spelled "DebugSwift" in a literal —
   keep such text out of shipping code. The phase runs on the build Xcode just
   produced, before any App Store processing.

Verify with a Release build:
```bash
cd iosApp
xcodebuild build -project CocktailCraft.xcodeproj -scheme CocktailCraft \
  -configuration Release -destination 'platform=iOS Simulator,name=iPhone 16e' \
  -derivedDataPath build/DerivedData
grep -a -c DebugSwift build/DerivedData/Build/Products/Release-iphonesimulator/CocktailCraft.app/CocktailCraft   # 0
```
(The build phase already runs this and the other checks; a successful Release
build means they passed.)

### Step 2: App Integration
DebugSwift is set up in `CocktailCraftApp.swift` (excerpt):

```swift
#if DEBUG
import DebugSwift
#endif

@main
struct CocktailCraftApp: App {
    #if DEBUG
    static var debugSwift = DebugSwift()
    #endif

    init() {
        KoinInitializer.instance.initialize()

        // Keep the widgets' snapshots current, except under the tests
        if !KoinInitializer.isTestMode {
            WidgetDataBridge.shared.start()
        }

        #if DEBUG
        setupDebugSwift()
        #endif
    }

    #if DEBUG
    private func setupDebugSwift() {
        configureNetworkMonitoring()
        configureCustomDebugActions()
        configureAppInfo()

        CocktailCraftApp.debugSwift.setup(hideFeatures: [], disable: [])

        // The accessibility-audit UI tests set HIDE_DEBUG_OVERLAY so they
        // audit only what ships
        if ProcessInfo.processInfo.environment["HIDE_DEBUG_OVERLAY"] == nil {
            CocktailCraftApp.debugSwift.show()
        }
    }
    #endif
}
```

## Final Configuration

### Project Settings (`iosApp/project.yml`)
```yaml
options:
  deploymentTarget:
    iOS: "17.0"
targets:
  CocktailCraft:
    settings:
      SWIFT_VERSION: "5.10"
      IPHONEOS_DEPLOYMENT_TARGET: "17.0"
```

After any `project.yml` change, regenerate: `xcodegen generate`.

### Swift Package (`iosApp/project.yml`)
```yaml
packages:
  DebugSwift:
    url: https://github.com/DebugSwift/DebugSwift
    revision: 3dc1781a855f3fa91c5f7fe3868717fe62ff3c4e   # tag 1.7.13.1

targets:
  CocktailCraft:
    dependencies:
      - package: DebugSwift
    settings:
      configs:
        Release:
          EXCLUDED_SOURCE_FILE_NAMES: DebugSwift.o
    # plus the "Strip DebugSwift from Release" postBuildScripts phase
```

### CocktailCraft-Specific Configuration

#### Network Monitoring
```swift
private func configureNetworkMonitoring() {
    // Monitor only TheCocktailDB API calls for focused debugging
    DebugSwift.Network.shared.onlyURLs = [
        "https://www.thecocktaildb.com"
    ]

    // Ignore analytics or other non-essential URLs if any
    DebugSwift.Network.shared.ignoredURLs = []
}
```

#### Custom Debug Actions
`configureCustomDebugActions()` in `CocktailCraftApp.swift` registers the
**CocktailCraft Debug Tools** group (listed under [Custom Debug Actions](#custom-debug-actions-1)
below). The actions act on the real stores through debug hooks, and the
screens update on their own because they observe the database.

#### App Information
```swift
private func configureAppInfo() {
    DebugSwift.App.shared.customInfo = {
        [
            .init(
                title: "CocktailCraft Info",
                infos: [
                    .init(title: "App Version",
                          subtitle: "\(Bundle.main.appVersion) (\(Bundle.main.buildNumber))"),
                    .init(title: "API", subtitle: "TheCocktailDB (Free Tier)"),
                    .init(title: "Platform", subtitle: "iOS (Kotlin Multiplatform)"),
                    .init(title: "Architecture", subtitle: "MVVM + Clean Architecture"),
                    .init(title: "DI Framework", subtitle: "Koin"),
                    .init(title: "UI Framework", subtitle: "SwiftUI")
                ]
            )
        ]
    }
}
```

#### Shake to Toggle
```swift
#if DEBUG
extension UIWindow {
    open override func motionEnded(_ motion: UIEvent.EventSubtype, with event: UIEvent?) {
        super.motionEnded(motion, with: event)

        if motion == .motionShake {
            CocktailCraftApp.debugSwift.toggle()
        }
    }
}
#endif
```

## Usage Guide

### Accessing DebugSwift
1. **Automatic**: The overlay appears on launch in DEBUG builds, unless the `HIDE_DEBUG_OVERLAY` environment variable is set (the accessibility-audit UI tests set it)
2. **Shake Gesture**: Shake device to toggle interface
3. **Manual**: Call `CocktailCraftApp.debugSwift.toggle()`

### Features Available
- **Network Inspector**: Monitor TheCocktailDB API calls
- **Performance Monitoring**: CPU, memory, FPS tracking
- **App Tools**: Crash reports, console logs, device info
- **Interface Tools**: View hierarchy, touch indicators
- **Resources**: File browser, UserDefaults viewer

### Custom Debug Actions
Access via: **App Tab → Custom Actions → CocktailCraft Debug Tools**

| Action | Debug hook (`KoinHelper`, `shared/src/iosTestMode/.../DebugTools.kt`) | What it does |
|--------|------------------------------------------|--------------|
| **Clear Favorites** | `debugClearFavorites()` | Removes the favorites of whoever is signed in (the guest's when signed out) |
| **Clear Cart** | `debugClearCart()` | Empties the current user's (or the guest's) cart |
| **Delete Every User's Data (cart, favorites, orders, reviews)** | `debugResetUserData()` | Deletes the cart, favorites, orders and reviews of every account on the device and of the guest, in one transaction. Accounts, sign-in, settings and the recently viewed lists stay |
| **Simulate Network Failure** / **Stop Simulating Network Failure** | `debugSetSimulatedNetworkFailure(enabled:)`, `debugIsSimulatingNetworkFailure()` | Makes every API request fail as a dropped connection would (retry, then cached data or the error UI) until toggled off; the device stays online as far as `NetworkMonitor` is concerned |

The hooks are compiled into Debug frameworks only (the `iosTestMode` source
set; see `includeIosTestMode` in `shared/build.gradle.kts`), so Release
builds contain neither the actions nor the hooks.

## QA Testing Scenarios

### Testing Network Connectivity
1. Open **Network tab**
2. Navigate through app (search cocktails, view details)
3. Monitor API calls to TheCocktailDB
4. Check response times and status codes
5. Verify JSON data structure

### Testing Performance
1. Open **Performance tab**
2. Navigate through different screens
3. Monitor CPU and memory usage
4. Check for memory leaks
5. Verify smooth FPS (60fps target)

### Testing Error Handling
1. Use the **Simulate Network Failure** action
2. Navigate through app features
3. Verify error messages display correctly
4. Check app doesn't crash, then **Stop Simulating Network Failure**

### Testing Data Persistence
1. Add items to favorites and cart
2. Use **Clear Favorites** or **Clear Cart**
3. Verify app handles empty states correctly

### Testing UI Components
1. Open **Interface tab**
2. Use **View Hierarchy** to inspect UI structure
3. Enable **Touch Indicators** to verify touch targets
4. Use **View Borders** to check layout issues

## Troubleshooting

### Build Errors
- **DebugSwift Not Found**: Let Xcode resolve packages (File > Packages > Resolve Package Versions) and check the `DebugSwift` entry in `project.yml` / `Package.resolved`
- **"DebugSwift is linked into the Release build"**: The Release link exclusion stopped matching — check the package object's name in the link file list and update `EXCLUDED_SOURCE_FILE_NAMES` in `project.yml`
- **Code Signing**: Normal iOS requirement, unrelated to DebugSwift

### Runtime Issues
- **Interface Not Appearing**: Check the DEBUG build configuration and that `HIDE_DEBUG_OVERLAY` is not set in the scheme's environment
- **Shake Not Working**: Verify device supports motion events; use manual toggle `CocktailCraftApp.debugSwift.toggle()`
- **Network Monitoring**: Ensure API calls are made to configured URLs (only `https://www.thecocktaildb.com` is monitored)
- **Performance Impact**: DebugSwift itself uses resources; this is normal in DEBUG builds
